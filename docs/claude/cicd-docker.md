# CI/CD e Docker Compose (Fase 6 — parziale)

Riferimento diretto usato per la struttura (stesso pattern prod/dev, stesso motivo): [Comune-di-Montesilvano/ComunicaPA](https://github.com/Comune-di-Montesilvano/ComunicaPA) — `docker-compose.yml` + `docker-compose.override.yml` + `.env.example`.

**`docker-compose.yml`** (produzione) — immagini da `ghcr.io/provincia-di-pescara/...`, **niente bind mount** (deploy non deve dipendere da un checkout del repo sull'host — unico volume named è `postgres_data`). `docker-compose.override.yml` (sviluppo) — build locale da `Dockerfile.dev`, bind mount per hot-reload, porte esposte. Attivato impostando `COMPOSE_FILE=docker-compose.yml;docker-compose.override.yml` in `.env` (mai in produzione); **attenzione**: se entrambi i file sono presenti nella stessa directory, `docker compose` li unisce automaticamente anche senza `COMPOSE_FILE` — per validare SOLO la produzione serve `docker compose -f docker-compose.yml ...` esplicito.

**`.env.example`** — solo bootstrap (Postgres, `JWT_SECRET`, porte). Tutto il resto (OIDC, SMTP, branding, parametrico) resta in DB via `impostazioni_sistema`/`parametrico_versioni`, mai in env — stesso principio di ComunicaPA (che deriva anche la chiave di cifratura dei settings da `JWT_SECRET`, esattamente come la nostra `oidc/crypto.ts`).

**Migration: NON girano come container** (decisione presa in sessione, dopo aver valutato e scartato un servizio `migrate` dedicato in compose). Le esegue `.github/workflows/release.yml` come job separato, con `docker run migrate/migrate` diretto contro `secrets.PRODUCTION_DATABASE_URL` — **gap esplicito**: quel secret non è ancora configurato, il job fa un no-op con warning finché non lo è. Serve prima decidere come il runner GitHub-hosted raggiunge il Postgres di produzione (rete privata → serve self-hosted runner, o endpoint esposto con allowlist — non ancora deciso).

**Backup** (`backup`, immagine `prodrigestivill/postgres-backup-local:18-alpine` — verificata via web il 2026-07-27: tag `18-alpine` esiste ed è mantenuta, non da training data): pg_dump giornaliero, rotazione 7/4/6 (giorni/settimane/mesi) di default, output su volume named `postgres_backups`, mai bind mount. **Bug reale trovato col bring-up**: `user: postgres:postgres` (dall'esempio nella documentazione ufficiale dell'immagine) fallisce con "insufficient permissions" su un volume named appena creato (proprietario root di default) — rimosso, l'entrypoint di default gira come root e sistema da sé i permessi al primo avvio. Ciclo backup→drop→restore verificato per davvero (non solo la doc): canary row sopravvissuta a dump+drop+restore, schema completo (45 tabelle) tornato intatto. Procedura in `docs/RUNBOOK-backup.md`.

**Tre bug reali trovati testando per davvero con `docker compose up` (non con `config --quiet`, che non li avrebbe mai presi)**:
1. **Postgres 18 ha cambiato convenzione della directory dati**: vuole un mount unico su `/var/lib/postgresql` (poi crea da sé una sottodirectory versionata), non più `.../data` come le versioni precedenti. Con `.../data` il container entra in restart loop lamentandosi di dati "unused" al vecchio path. Mai emerso nei test precedenti in sessione perché ogni container Postgres usato prima era effimero, senza volume named persistente — questo bug esiste solo con un volume reale, che prima di ora non avevamo mai avuto in questo progetto.
2. **`Dockerfile.dev` del backend senza `.dockerignore`**: `COPY . .` copiava anche il `node_modules` locale dell'host (Windows, con symlink pnpm assoluti tipo `C:/Users/...`) SOPRA quello appena installato nel container Linux durante il build, rompendo la risoluzione dei moduli a runtime (`ERR_MODULE_NOT_FOUND` su `pg`). Il volume named `backend_node_modules` viene seminato dal contenuto dell'immagine alla prima creazione — se l'immagine ha il `node_modules` sbagliato, lo eredita anche il volume. Fix: `.dockerignore` con `node_modules` (aggiunto anche a `engine-go/` per igiene, anche se lì non era necessario: `Dockerfile.dev` di Go non fa `COPY` affatto, il sorgente arriva solo da bind mount).
3. Non un bug del progetto ma un promemoria confermato: `docker exec` su Postgres con `POSTGRES_USER` diverso da `postgres` (qui `polaris`) richiede `psql -U polaris` esplicito — il ruolo DB di default non esiste con un altro nome.

**`.github/workflows/ci.yml`** — due job paralleli (`engine-go`, `backend-node`), ciascuno con un service container Postgres 18 (stesso pattern degli ephemeral container usati manualmente tutta la sessione, qui automatizzato), migration applicate via `psql -f` prima dei test, poi build/vet/gofmt/test per Go e typecheck/test per Node — inclusi i test che richiedono `TEST_DATABASE_URL` (skippati finora in locale se non impostata, qui sempre eseguiti). Terzo job valida `docker compose -f docker-compose.yml config --quiet`.

**`.github/workflows/release.yml`** — build+push di `polaris-engine`/`polaris-backend` su push a `master` (tag `:dev`) e su tag `v*` (tag `:vX.Y.Z`+`:latest`), più il job `migrate` sopra descritto. **Gotcha reale, confermato applicabile qui**: il nome org (`Provincia-di-Pescara`) ha maiuscole — `ghcr.io` rifiuta namespace non lowercase, quindi il namespace immagine è hardcoded (`provincia-di-pescara`) invece di derivato da `github.repository`. Stesso identico problema documentato da ComunicaPA, stessa causa.

Versioni Actions verificate via API (non assunte): `actions/checkout@v7`, `actions/setup-go@v7`, `actions/setup-node@v7`, `pnpm/action-setup@v6`, `docker/build-push-action@v7`, `docker/login-action@v4`, `docker/setup-buildx-action@v4`.

## Frontend (`frontend-pubblico`/`frontend-backoffice`) wired nel compose

Entrambi i frontend erano nel workspace da settimane con `Dockerfile`/`Dockerfile.dev` propri ma **nessuno dei due era mai stato aggiunto a `docker-compose.yml`/`.override.yml` né alla matrice build-push di `release.yml`** — non solo `frontend-pubblico` come il vecchio residuo noto in CLAUDE.md faceva pensare, il gap era identico su entrambi.

**Niente reverse proxy condiviso davanti allo stack** (quella è ancora una decisione architetturale esplicitamente aperta, vedi `docs/SPEC.md`): i due frontend chiamano API su path relativi (`baseUrl() === ''`, same-origin per costruzione — anche il cookie di stato OIDC anti-CSRF lo richiede). Soluzione scelta: ogni frontend fa da mini-reverse-proxy di se stesso via `nginx.conf` (`proxy_pass http://backend:8080` sui prefissi esatti già usati dal proxy Vite in `vite.config.ts` — `/auth`, `/pubblico`, `/stagioni`, `/organismi-sportivi` per il pubblico; `/auth`, `/backoffice` per il backoffice), fallback SPA (`try_files $uri /index.html`) per tutto il resto. Stesso identico principio del proxy Vite, solo la versione prod. In dev containerizzato (`docker-compose.override.yml`) il target del proxy Vite non può restare `localhost:3000` (irraggiungibile dentro un container) — reso configurabile via `VITE_BACKEND_PROXY_TARGET` (default invariato per lo sviluppo locale non containerizzato).

**Tre bug reali trovati verificando col bring-up (non con `config --quiet`)**:
1. **`frontend-backoffice/Dockerfile` non copiava mai un `nginx.conf`** — nginx serviva con la config di default (nessun fallback SPA). Innocuo finché nessuno provava un deep-link o un refresh su una rotta diversa da `/`: il backoffice usa `react-router` con `createBrowserRouter` (path reali, non solo tab state come il pubblico), quindi avrebbe dato 404 grezzo da nginx invece del router client-side. `frontend-pubblico` aveva già il suo `nginx.conf` corretto (commentato esplicitamente per `/oidc/callback`, target di hard-navigation) — il backoffice l'aveva semplicemente perso o mai avuto.
2. **`pnpm build` (`tsc && vite build`) falliva nel contesto Docker** (ma non in CI, dove il checkout è l'intero monorepo): `tsc` sul `tsconfig.json` principale include anche i file di test, e `testUtil/creaPersonaTest.ts`/`creaUtenteTest.ts` importano da `../../../backend-node/src/...` (helper JWT riusati nei test end-to-end) — un import cross-package valido solo quando la cartella `backend-node` è un sibling reale sul filesystem, mai vero nel build context Docker (`context: frontend-pubblico`/`frontend-backoffice`, scoped al solo pacchetto). Fix: `tsconfig.build.json` (extends la config base, esclude `**/*.test.ts(x)` e `testUtil/**`) usato solo da `pnpm build` (`tsc -p tsconfig.build.json && vite build`) — `pnpm typecheck`/l'IDE restano sulla config completa, che deve continuare a vedere anche i test.
3. **`ports:` si concatena tra `docker-compose.yml` e `.override.yml`, non si sovrascrive** (a differenza di scalari come `image`/`environment` per chiave) — un frontend containerizzato in dev espone la porta di Vite (5173/5174), non quella di nginx (80) della build prod: riusare la stessa variabile d'ambiente con default diverso in entrambi i file avrebbe lasciato attivo anche il mapping prod (porta 80 morta, nginx non gira nell'immagine dev) insieme a quello dev. Fix: variabili distinte — `FRONTEND_*_PORT` (prod, verso nginx:80) vs `FRONTEND_*_DEV_PORT` (dev, verso Vite).

Verificato con bring-up reale (non solo `docker compose config`): stack dev (`postgres`+`engine`+`backend`, migration applicate a mano con `migrate/migrate` contro il volume named appena creato) + i due container prod (immagini nginx buildate localmente, avviate con `docker run` sulla stessa rete Docker del compose) — statico servito, SPA fallback su deep-link (incluso il fix del bug backoffice), proxy `/auth`/`/pubblico`/`/stagioni`/`/organismi-sportivi`/`/backoffice` tutti raggiungono il backend reale (401 sugli endpoint autenticati, non 404 — prova che il routing nginx→backend funziona, non solo che nginx risponde).

**Gotcha CI reale trovato il 2026-08-02**: `backend-node/pnpm-lock.yaml` è un secondo lockfile, DISTINTO dal `pnpm-lock.yaml` di workspace alla radice — il `Dockerfile` di produzione fa `COPY package.json pnpm-lock.yaml` e un `pnpm install --frozen-lockfile` standalone dentro `backend-node/`, mai coperto da `pnpm install` lanciato alla radice (che aggiorna solo il lockfile di workspace). Risultato: `multer`/`@types/multer` aggiunti a `package.json` (commit `9383e85`) senza mai rigenerare questo lockfile standalone — mai fallito in locale, mai in CI finché non è arrivato un build Docker reale su quel branch. Fix/verifica: `cd backend-node && pnpm install --ignore-workspace --lockfile-only`, poi verificare con `pnpm install --frozen-lockfile --ignore-scripts --prod --ignore-workspace` su una copia pulita (`package.json`+`pnpm-lock.yaml` in una dir vuota) prima di committare — replica esattamente lo step Docker che fallirebbe altrimenti.

`gh run list --branch master --limit N` / `gh run view <id>` (`--log-failed` per il solo step fallito) — per controllare l'esito CI/Release dopo un push senza aprire il browser. Sempre controllare dopo un push su master, non solo confidare nel proprio job locale verde (vedi gotcha pnpm-workspace del 2026-07-27, stesso principio: un file condiviso può rompere un altro job silenziosamente).
